# MOA 라벨 쏠림 원인 재감사·실행 설정 수정 — 2026-10-20

## 결론

**정상 오탐 17/18(94.4%)인 연구 모델은 여전히 사용 불가다.** 이번에는 모델을 더
학습하거나 추론하지 않고, 기존 실행 기록·점수·optimizer/RNG·실제 토크나이저를
재검사했다. 학습 후보 8/8과 기존 평가 예약을 그대로 유지했다.

선택지 순서만의 문제가 아니다. 새 구간 후보는 정상 15/18건을 어느 순서로 줘도
오류로 판단했다. 순서를 평균한 점수의 정상/오류 구별 능력(AUC)은 0.435였다.
0.5가 무작위 순위 기준이며, 이 값은 정확도 43.5%를 뜻하지 않는다.

실제 설정 오류도 찾았다. 4 epochs × train 144 / 누적 8 = **72 updates**인데
scheduler horizon은 **120**으로 남아 있었다. 실제 데이터/epoch/누적/상한으로 계획을
계산하고, 실행되는 설정과 선언이 다르면 거절하도록 수정했다.
이것이 성능 붕괴를 얼마나 일으켰는지는 재학습 대조 없이 단정하지 않는다.

## 1. 먼저 바로잡은 과거 설명

직전 보고서의 "선택지 섞기 꺼짐"은 확인 오류였다. 라이브러리 기본값만 보면
꺼져 있지만, 실제 JOB은 `shuffle_options=["choice"]`로 설정했고 실제 실행에 적용됐다.

- `JOB-r4.json` SHA = 실제 `TRAIN_RESULT.json.job_sha256`.
- 고정 실행 러너 SHA와 설치된 `laya.train` SHA도 JOB과 일치했다.
- 원래 144문항을 4 epochs 동안 같은 seed/행 순서로 다시 토크나이즈했다.
- **576개 선택지 배치, 6개 순열 모두 사용, 정답 위치 오류 0건**.
- 재현한 마지막 option RNG가 저장된 학습 상태의 RNG와 정확히 같았다.

| 실제 정답 | 위치 1 | 위치 2 | 위치 3 | 합계 |
| --- | --- | --- | --- | --- |
| 정상 | 39 | 54 | 51 | 144 |
| 오류 | 90 | 90 | 108 | 288 |
| 근거 부족 | 42 | 54 | 48 | 144 |

무작위 셔플이므로 완전한 같은 횟수는 아니지만, 정답이 한 위치에 고정되지는 않았다.
설치된 LAYA의 target 순열과 soft-CE gradient 방향도 실제 라이브러리 단위 테스트로
확인했다. 이 검사는 모델 forward나 LAYA optimizer update가 아니다.

## 3. 저장된 학습 상태의 실제 수치

- 실제 optimizer updates / scheduler step: 72 / 72.
- 첫 8회 평균 loss: 1.23644 → 마지막 8회 평균: 1.02815.
- 원래 라벨 비율 정상 36 / 오류 72 / 근거 부족 36만 사용하는 상수 예측의
  soft-CE: 1.03972. 마지막 미니배치 평균과 완전히 같은 분포의 지표는 아니므로
  "완전히 동일한 모델"이라고 단정하지 않고, underfitting의 보조 근거로 사용한다.
- gradient norm 최솟값 0.6513, 최댓값 8.8078, nonfinite loss 0.
- 저장된 scheduler T_max: 120.
- 72회 종료 시 실제 learning rate: 0.000346146.
- 실제 72회에 맞춘 계획이라면 종료 목표 min_lr는 0.000001이다.

업데이트를 더 채우려고 epoch나 데이터를 늘리지 않았다. 시간/업데이트/후보 예약을
초기화하지 않았고, 기존 후보의 optimizer·scheduler·체크포인트는 수정하지 않았다.

모델 config의 `training.updates=15987`은 부모에서 상속된 메타데이터였다.
이번 연구의 실제 72회라는 증거는 연구 영수증/optimizer에 있다. 앞으로 저장되는
연구 모델은 실제 run/update/cursor/실행 계약 SHA를 쓰고, 부모 기록은 별도 보존한다.

## 5. 실제 코드 수정

1. `r2_research.training_plan()`이 데이터 수, 부분 누적 window, epochs,
   최대 updates 중 실제 먼저 끝나는 길이로 scheduler horizon을 계산한다.
   선언된 시간/epoch/update 상한은 늘리지 않는다.
2. 일반 publisher와 구간 publisher가 같은 계산을 사용한다. 명시적인 기존
   balanced sampler를 사용하는 경우에만 그 실제 item 수를 반영한다.
3. 워커가 모델을 불러오기 전에 계획 일치를 검사한다. 현재 러너가 구현하지 않는
   loss/microbatch/AMP/layout 등 설정을 조용히 무시하지 않고 거절한다.
   과거 실제 실행은 soft-CE였으므로, 잠재적인 미지원 설정 차단을 과거의 확인된
   붕괴 원인이라고 부르지는 않는다.
4. 미래 실행은 effective LAYA config·라벨 수·구현/입력 해시를 별도
   `TRAINING_CONTRACT.json`으로 고정하고, 저장본과 영수증에 계약 SHA를 연결한다.
5. 기존 발행 폴더를 다시 덮어쓰는 것을 거절한다. 과거 run_id/예산/모델은 보존한다.
6. 캐시 분석기는 서로 다른 모델/문항/정답·중복·누락·규칙 강제 답의 혼입을 거절한다.

기존 고정 실행본은 덮어쓰지 않았다. 새 코드가 과거 후보를 몰래 재개하거나
운영 모델로 승격시키지 않으며, 이번에 새 학습 JOB을 발행하지 않았다.
