프로세스 이름·RSS만 조사했으며 문서 제목·명령 인자·환경변수·비밀은 수집하지 않았다.

## 바꾼 부분과 실측

기존 저장은 MPS에서 FP16 임시 사본을 만든 뒤 CPU로 복사했다.
CPU로 먼저 옮긴 뒤 FP16으로 저장하고, 해시는 큰 bytes 사본 없이 같은 바이트를 읽도록 했다.
스냅샷 뒤에는 이번 연구 프로세스의 사용하지 않는 GPU 캐시만 정리한다.
실제 FP32 학습 파라미터·encoder 동결·입력·질문·선택지·라벨·학습률·배치·예산은 바꾸지 않았다.

- 128MiB 합성 GPU 텐서 시험: 기존 저장의 잔류 캐시32MiB가 관찰됐고 CPU 우선 저장은 그 추가 GPU 캐시를 만들지 않았다. 저장 바이트는 동일했다.
- 실제 원본 R1, **학습 없이** 로딩→해시→CPU 우선 저장: 7.36초. 0.1초 간격 표본에서 가용 메모리 최저 약3.88GiB, 프로세스 RSS 최대 약1.92GiB였다.
- 이 실제 모델의 export 파일 SHA-256은 원본 R1과 같았다. 원본·운영 registry/manifest·살아 있는 파라미터도 변경되지 않았다.
- 실제 S1 재개 후 별도 표본의 가용 메모리는 약3.47GiB, 메모리 압력·기존 train_allowed는 정상이었다. 이것은 연속적인 학습 최대 메모리 측정이나 무영향 보증은 아니다.

이전의 임시 로딩 전7GiB 진입 기준은 새 실측의 최대 가용량 감소+기존3GiB+추가512MiB를 512MiB 단위로 올림해 **5GiB**로 재산정했다.
**학습 중 원래3GiB 기준, AC 전원, 15분 유휴, 메모리 압력·디스크·device.lock 보호는 그대로다.**
조건을 벗어나면 저장 후 멈춘다. 워터마크 확대·시스템 purge·강제 앱 종료·정밀도 축소는 하지 않았다.
`empty_cache`는 사용하지 않는 캐시만 해제한다는 [PyTorch 공식 문서](https://docs.pytorch.org/docs/stable/mps.html)와 실제 측정을 함께 확인했다.
