# MOA 오류 판별 모델 정확도 점검·개선 — 2026-10-18

37.5%는 모바일 HTML 변환 자체의 정확도가 아니라 **맥북 LAYA의 합성 오류 판별 시험 점수**다.
이 점수로 자동 승인·공개를 맡길 수 없다. 실자료 20건의 기존 원문/HTML/규칙/브라우저 검증 기록과
이 모델 시험 점수는 서로 다른 지표다. 실자료 사람 승인은 여전히 0건이다.

## 왜 기존 학습에서 정확도가 오르지 않았나

확인된 사실과 추정을 구분한다.

- 기존 분리 시험 200문항은 학습 전후 모두 75개 정답(37.5%). head 파라미터 변경과
  저장·재로딩 일치는 확인됐으므로, 미실행이나 저장 실패가 원인은 아니다.
- **학습/실행 입력 형식 불일치를 발견했다.** 묶음 JSON의 정렬 때문에 학습 선택지는
  changed/insufficient/preserved 순서인데 워커는 preserved/changed/insufficient 순서다.
  상태의 최상위 항목 순서도 다르다. LAYA는 JSON 삽입 순서를 실제 토큰에 반영한다.
  계약용 정렬 해시는 이 차이를 구분하지 않으므로 계약 일치만으로는 충분하지 않다.
- 개선용 calibration 200문항에서 기존 기준 모델을 같은 원문/정답으로 측정하면,
  파일 형식 그대로 36.5%, 선택지만 실행 순서로 39.0%, 상태까지 실행 순서로 42.5%다.
  **입력 순서가 실제 판정에 영향을 준다는 증거**이지, 더 잘 나온 형식을 골라 정확도를 올렸다는 뜻이 아니다.
  실행 형식은 이미 운영 워커가 쓰는 것을 기준으로 고정한다.
- 같은 실행 형식에서 기존 학습 후보는 calibration 43.0%, 학습 600문항에서도 41.83%다.
  학습 자료조차 충분히 구별하지 못하는 underfitting 증거다. 단지 새 양식 일반화만의 문제가 아니다.
- calibration의 학과-교실 교환 10건과 중요 조건 삭제 10건은 기존 후보가 전부 놓쳤다.
  오류 110건 중 64건을 preserved로 잘못 판단했다. 근거부족을 preserved로 본 13건도 별도 기록한다.
- 정답 분포는 preserved 35% / changed 55% / insufficient 10%다. 기존 점수는
  항상 changed만 고르는 55% 기준선보다도 낮다. 전체 정확도만 보고 성공으로 판정하면 안 된다.
- 업데이트 38회, 고정 선택지, 적은 합성 양식의 영향은 개선 실험 대상이다.
  각각의 기여도를 분리한 다회 ablation은 하지 않았으므로 하나만 단독 원인으로 확정하지 않는다.

정답 위치 매핑, 묶음 SHA, 문맥 길이와 저장 가중치를 실제 설치된 LAYA에서 점검했다.
기존 모델은 `jhu-clsp/mmBERT-base` 기반이며, 언어권을 추측해 모델을 교체하지 않았다.

## 실제 코드 수정

- `prepare_training_rows`: 원본 묶음·정답·분할을 고치지 않고 학습 입력만 실제 워커의
  state/question 순서와 맞춘다. 잘못된 질문을 정상 질문으로 몰래 치환하지 않고 거부한다.
  state에 정답·분할 등의 힌트가 있으면 거부한다.
- 실제 맥북 LAYA `serialize_state`와 질문 직렬화로 1,000행 실행 형식 일치를 확인했다.
- raw 모델 판정에 대해 다수 클래스 기준선, 클래스별 혼동표·재현율, balanced accuracy,
  macro F1, 오류/근거부족을 정상으로 잘못 본 수, 질문별·변형별 상세 결과를 추가했다.
- `audit`는 train/calibration만 허용한다. 기존 평가 전용 자료·미확인 보류·모델 자기 판정·JEV를
  정답으로 넣거나 시험 자료를 학습에 옮기지 않는다. 확률 보정도 이번에 맞추지 않는다.
- 사용자에게 허용받은 추가 1회만 별도 예약한다. 기존 두 예약·가중치를 보존하며,
  같은 승인을 재사용할 수 없다. 일반 주간 2회 제한을 영구 완화하지 않는다.
- 완료 업데이트 직후 **가중치/해시/학습 영수증부터 먼저 저장**하고 평가를 별도 프로세스로 분리했다.
  `checkpoint_saved_pending_evaluation`과 `completed`를 구분한다. 평가만 재실행할 때는 optimizer를
  호출하지 않는다. 평가 batch는 1로 줄여 peak 메모리를 낮추며, 기존 검증용 자원 기준을 유지한다.
- 중단 시 자원 상태와 단계를 별도 기록한다. 학습 자원 기준을 낮추거나 유휴 조건을 우회하지 않는다.
